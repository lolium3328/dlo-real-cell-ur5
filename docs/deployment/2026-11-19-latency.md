# 2026-11-19 决策延迟优化

## 计划

1. 用部署包里的录制帧定位耗时，并核对 Windows 的计时精度。
2. 优先减少规划中重复坐标运算的开销，用同一批输入对比计算结果、策略输出和延迟。
3. 用保留 80 ms 门槛的离线预检验证，并记录模拟运行结果。

## 基线

部署策略每 80 ms 尝试更新一次动作。真机默认使用异步规划。在新动作返回前，125 Hz 控制循环继续使用上一次规划结果，并继续执行低层约束检查。规划耗时越长，新动作使用的观测就越旧，尤其会影响球经过绳子时的避让时机。部署包的仿真说明记录了加入 80 ms 决策延迟后，成功率从 85% 降到 81%。

前一轮诊断中，默认配置 p95 为 125 ms，临时增加 Torch 线程后的最佳 p95 为 94 ms。两者均高于 80 ms 门槛。Windows 上现用 Python 3.11 的 `monotonic()` 分辨率为 15.625 ms，`perf_counter()` 为 0.0001 ms。

## 改动

- 球到线段距离按坐标计算，视觉匹配减少中间数组，绳段迭代直接使用切片。Hildreth 求解器用三个标量做原有的逐行迭代。采样数、规划步长和安全阈值保持原值。
- 预检、伺服循环、相机和异步线程使用同一高精度时钟。相机启动阶段要求两路图像都在现有 100 ms 有效期内，避免用已过期帧初始化。
- `--torch-threads` 同时配置录制帧预检和实际策略。默认仍为 1，本机验证时显式传入 3。运行时 BLAS 仍限制为单线程。

## 验证结果

| 测试 | 结果 |
| --- | --- |
| 线段距离微基准（100 次） | 154.4 ms 降到 43.0 ms，比较样本的距离完全一致 |
| 提交版本的数值对照 | 350 组三维约束的求解输出和迭代次数一致。53 种绳链长度的切片迭代结果一致 |
| 录制帧原型重复 60 次决策 | 3 个 Torch 线程的 p95 为 71 ms，标量求解前后的策略动作和末端指令一致 |
| `--dry-run --torch-threads 3` | 30 次决策 p50 为 61.0 ms、p95 为 74.0 ms，软件预检通过。随后模拟策略在 E105 停止，符合部署说明中 stub 的已知行为 |
| 最终软件预检复测（3 线程） | 30 次决策 p50 为 61.2 ms、p95 为 77.4 ms，软件预检通过，156 个文件通过 SHA-256 校验 |
| 录制帧异步回放（30 Hz 输入，固定机械臂状态） | 1、2、3 个 Torch 线程的规划 p95 分别约 151、144、137 ms，每组 46 次决策 |
| 实时渲染软件在环 | `test_reach_0087` 在 1、2、3 个 Torch 线程下分别测得规划 p95 约 590、773、727 ms，三次均因 E105 停止 |

录制帧预检已通过，异步回放和实时闭环仍有明显性能缺口。实时渲染与仿真物理额外占用本机资源，其结果不能直接当作真机延迟。下一步优先缩短视觉和规划并行时的长尾，或在更快的控制电脑上重复同一组录制帧、异步回放和软件在环检查。实机检查尚未完成。
