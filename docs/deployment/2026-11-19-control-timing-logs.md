# 真机闭环时序记录

## 计划

为 2026-11-19 的 `test_reach_0087` 补齐诊断数据。该次运行的 866 个控制步中，654 步报告 `observation_stale`。这些步的估计年龄都超过 100 ms。旧日志无法确定时间消耗发生在相机到帧、绳形估计、线程交接还是规划计算。保留既有运动和停机条件，分开记录各环节的时间和状态，场景退出后统一写入文件。

## 日志字段

新日志与已有控制和伺服日志共同保存在会话的 `outputs/real_runs/<时间>/<场景>*.jsonl` 下。

| 文件或事件 | 时间和关联字段 |
| --- | --- |
| `<场景>_timing.jsonl` 的 `camera_frame` 和 `camera_error` | 相机角色、等待开始、主机收到帧时间、可供跟踪读取时间、延迟补偿后的 `frame_s`。设备侧记录帧号、时间戳和时钟域。帧等待或复制异常单独记录，每个相机最多每 0.5 秒记一次。 |
| `tracker_start` 和 `tracker_publish` | 读取的帧时间 `input_frame_s`、绳形估计参考时刻 `tracker_sample_s`、`observed_s`、计算完成 `computed_s`、发布时间 `t_s`、线程 CPU 用时、双视角支持点数、有效证据时间和质量门控各判据。无新帧时的更新对应空帧列表。发布记录的 `tracker_id` 等于开始事件的 `event_id`。 |
| `planner_start` 和 `planner_publish` | 输入绳形、夹持端和球的参考时间、规划开始、模型更新完成 `model_ready_s`、规划计算完成、发布时间和线程 CPU 用时。发布记录的 `plan_id` 等于开始事件的 `event_id`。 |

## 如何排查

1. 在控制日志里找 `observation_stale`。查看 `stale_reasons`。它可以同时包含 `result_age`（异步结果年龄超过 0.1 s）、`quality_gate`（图像证据不足）和 `ball_missing`（缺少有效球位置）。同步模式当步计算估计，状态判定使用后两项。
2. 用该行的 `tracker_id` 找发布记录。用 `computed_s - tracker_start.t_s` 估计识别和门控耗时，用发布时间减去 `computed_s` 查看计算完成到发布的间隔。用 `inputs_read_s - tracker_published_s` 查看发布到被异步控制步读取的间隔。
3. 用 `(role, frame_s)` 匹配跟踪输入与相机记录。比较连续帧的主机到达间隔、设备帧号以及主机收帧到跟踪读取的间隔。场景启动之前缓存的帧可出现在 `scene_start.cached_frame_s`。
4. 通过 `plan_id` 关联规划开始和发布。把规划和跟踪的时间区间对在一起，再比较各自线程 CPU 时间。线程 CPU 时间只计当前线程，Torch 和 OpenCV 的其他工作线程耗时不会被计入。
5. 若停机，按 `scene_terminal.step_id` 找到触发的控制或伺服步。查看该步的原始状态和错误报告中的停机判据。

后缀为 `_s` 的时间使用同一主机的单调时钟，闭环启动时为 0，准备阶段可能为负。球时钟 `s` 从首次进入跟踪开始。设备时间戳是各自时钟域的毫秒值。日志表头的 `anchor_unix_ns` 和 `anchor_scene_s` 可用于近似对齐会话的墙上时间。事件按写入内存的顺序排列，比较时间应使用 `t_s`。缓冲区最多记录 65,536 个常规事件，表头的 `dropped_events` 报告溢出数量，场景终止事件独立保留。

## 验证结果

- 使用假帧验证了序号、设备时间、主机收帧时间以及补偿后的帧时间。使用假跟踪和规划输入验证了结果编号可关联，`result_age` 和 `quality_gate` 同时触发时均能记录。
- 用内存替身执行场景控制循环，注入 `observation_fault`。控制 JSONL 保留最后一步，时序记录指向同一步，并记录了两路停止调用返回。检查新日志可逐行按 JSON 读取。
- 使用假数据验证了同步控制的估计和规划编号，以及缓冲区满后保留终止事件。两个部署副本各自通过了 157 项部署文件哈希校验。
- 以上验证未连接真机或打开相机。真实相机、识别和规划的时序数据将在下一次现场闭环运行时产生。
