# 双 UR5 (CB3) 实机部署说明（v39 r10 策略，v41 UR5 演示场景 test_reach_0087）

本包用于在实机上运行 v39_occlusion 策略（`ckpt_r60.pt`，commit 3 / 0.1 / 0.2）完成演示场景 test_reach_0087：左臂由策略闭环控制，右臂按场景脚本中的已知球轨迹运动。

## v42 更新（2026-11-19 晚：整体放慢 6 倍，录两个视角的视频）

- **合并。** 本包 = v41（UR5 场景、控制器底座坐标系）+ 现场电脑上的 6 个提交（Windows 预检、精确计时、CB3 识别、时序日志）。2026-11-19 20:58 那次实机运行用的是旧 v40 包，所以出现了 2.87 / 2.91 rad 的“关节分支”警告；用本包重新做可行性检查。
- **为什么放慢。** 那次运行的时序（`<场景>_timing.jsonl`）：绳形跟踪约 120 ms 一次，规划 p50 368 ms，从相机出帧到动作生效 p50 0.46 s。训练里这段只有约 0.05 s，决策周期 80 ms。另外跟踪结果超过 0.1 s 就判过期，球开始动以后 92% 的控制步被判过期、指令为零，左臂 6.5 s 只动了 1.7 mm。
- **`--time-scale 6`（默认）。** 球、左臂、决策周期、场景时限一起放慢 6 倍。控制器内部用“真实时间 / 6”的仿真时钟，所以策略看到的速度、年龄、每次决策的位移都和训练时一样，不用重训。真实数值：
  - 决策周期 0.48 s（大于规划 p95 0.40 s）
  - 左臂最大 8.3 mm/s，球最快约 8 mm/s
  - 跟踪过期阈值相当于真实 0.6 s
  - 成功前保持 2.4 s，场景时限 180 s；test_reach_0087 全程约 65 s
  - 控制线程每 48 ms 算一步，伺服仍是 125 Hz，在两步之间线性插值
- **验证。** 真实延迟换算到仿真时间是 80 ms 决策周期里有 8–10 步还在执行上一个动作。`latency_sim.py` 在 5 个演示场景上 async:8 和 async:10 都是 5/5 成功。软件在环（`sil_check.py`，真实时间的绳子仿真 + 渲染图像 + 跟踪器，额外加 0.09 s 跟踪、0.31 s 规划的延迟模拟现场电脑）：test_reach_0087 成功，真实 rmse 5.6 mm，球绳最近 31 mm，球开始动以后没有一步被判过期。
- **录像。** 每次运行录 `<场景>_front.avi`、`<场景>_top.avi`（MJPG，10 fps，按真实时间播放）和 `<场景>_video.json`（每帧的相机时间，和其他日志的 *_s 同一时钟）。编码每帧约 1.7 ms CPU、单线程，两路合计约占一个核的 3%，不阻塞跟踪和规划线程。`--no-video` 关闭。
- **换球（`--sphere-radius`、`--sphere-centre-behind-tip`）。** 训练用的球半径 40 mm，球心在探针尖后（法兰一侧）25 mm。换了球就把实测值传给这两个参数（单位 m），可行性检查、球与左臂间隙、球绳中止判断、控制器的保护距离和 CBF、由右臂 TCP 推算球心，全部用同一个值。策略网络的输入里没有半径，不用重训，但每个场景都要先 `--check-only` 复验。仿真（6 倍缩放下的延迟，5 个演示场景）：半径 40 / 45 / 50 / 60 mm 分别 5/5、4/5、3/5、3/5 成功，test_reach_0087 都成功，球绳最近 40.9 / 36.0 / 31.0 / 21.0 mm——余量基本按半径的增量减少，策略不会因为球大而躲得更远。test_reach_0087 的球与左臂保守间隙（左臂在整个工作区任意位置）在 40 / 50 / 55 mm 时为 11.3 / 1.3 / -3.7 mm，半径超过约 51 mm 可行性检查就不通过；那时应按新半径重新生成场景（必要时重训），不要直接 `--ignore-check`。
- **仿真轨迹参考。** `outputs/cell_calibrated_20261113/v41_ur5/trajectories/test_reach_0087_sim_tcp.csv`（说明在同名 .json）：同一策略在仿真里按部署延迟跑 test_reach_0087（成功，球绳最近 40.9 mm）的每个 8 ms 步。左右 TCP 都是各自控制器 base 坐标系下的 UR 位姿 `[x y z rx ry rz]` 加关节角，右臂和 runner 的规划完全一致；`t_real_s` 是 6 倍缩放下真机到达同一状态的时间。用于对照示教器读数和真机日志；开环回放左臂不等于策略控制。重新生成：`scripts/real_cell/export_sim_trajectory.py --scene <场景>`。
- 日志里的 `s`（球时钟）是仿真时间，其余 `*_s` 都是真实秒。`--time-scale 1` 恢复原来的实时运行（现场电脑的延迟下仿真里会碰绳，不要用）。

## v41 更新（2026-11-19，换成 UR5）

- 现场是两台 **UR5 (CB3, PolyScope 3.15)**，之前的仿真和检查都是按 UR5e 做的。v41 把仿真里的两条臂换成 UR5（ROS-Industrial ur_description 的运动学和外形），仿真 TCP 与 UR5 控制器 DH 运动学一致（误差 0.0 mm）。
- 仿真底座坐标系改成和 UR 控制器的 base 坐标系一致（以前差 180°，同一组关节角肩部读数差 π）。现在仿真关节角 = 真机关节角，预检里“仿真运动学 vs 机器人 TCP”的对比才成立。
- 右臂底座标定的旋转（约 0.5°）以前没有生效，现在生效了。
- 右臂夹球姿态：在 v40 姿态基础上绕探针轴转 90°（球在探针轴上，位置不变）。原姿态在 UR5 上法兰平板会碰前臂。四元数 wxyz = (-0.109382, 0.640856, -0.640856, -0.408218)，世界坐标系（= 左臂控制器 base）。
- 规划时右臂姿态直接用这个验证过的姿态，不再沿用右臂当前姿态；归位时 moveJ 会转到位。
- 目前只有 test_reach_0087 在 UR5 上完整复检通过（策略成功，球绳最近 43.3 mm，两臂、自碰、桌面立柱、绳子间隙都在限值以上），默认只跑这一个场景。下文提到的其他场景和数字是 v40 (UR5e) 的，仅供参考。
- CB3 没有 e-Series 的“远程控制”开关：E501 时先停掉示教器上的程序、关掉弹窗，确认没有别的 RTDE / External Control 客户端连着。

- 世界坐标系就是左臂底座坐标系。
- 两臂的 TCP 都设为探针尖端 `[0, 0, 0.165, 0, 0, 0]`。
- 左臂工具姿态取开始前的状态，归位过程中不旋转；右臂工具姿态用配置里验证过的姿态（见上），归位时会转过去。

## 0. 部署前必须知道的风险

下面几项都还没有在实机上验证过。每一项都可能导致失败，第 3、6 项还可能导致碰撞。

1. **策略只在 headless 跟踪模型下训练和评估过。** 2026-11-19 在仿真里改用真实的跟踪器（`RecordedRopeTracker`），在渲染图像上跟踪、不加延迟，跑了全部 62 个测试场景：
   - 成功率从 53/62（85%）降到 48/62（77%）。
   - 超时从 1 个增加到 7 个。这些超时都是差一点没达标：rmse 中位数 13.6 mm（标准 ≤ 12 mm），末端中位数 20 mm（标准 ≤ 16 mm），都没有碰撞。
   - 5 个演示场景里只有 test_reach_0087 和 test_reach_0016 成功。test_reach_0090、test_hold_0085、test_hold_0116 都是超时，没有碰撞。
   - 真实相机图像只会比渲染图像更难。
2. **`ur_rtde` 的控制接口还没在任何控制器上跑通过。** 在 URSim 上，RTDE 控制同步一直失败；只读接口是正常的。所以 `servoJ`、`servoL`、`moveJ`、`moveL` 以及安全限位查询，第一次真正执行就是在实机上。
3. **相机外参之前的独立验证误差约 19 mm / 5.8°。** 这个误差会直接进入中心线估计、成功判断、CBF 和球绳间隙中止判断。
4. **两个底座之间的变换用的是仿真值。** 双探针对点检查用来核对它，误差必须 ≤ 5 mm。
5. **工具尺寸是估计值。** 两臂间隙按胶囊模型计算，工具段半径取 40 mm。仿真回放中两臂最小间隙为 25 mm（test_hold_0085）。
6. **程序只检查两臂之间、球与左臂之间的间隙。** 各臂的自碰撞，以及与桌面、立柱、相机支架的碰撞，完全依赖示教器上配置的安全平面和关节限位。

## 2. 电脑环境

1. 把整个文件夹从移动硬盘拷到电脑本地磁盘。不要直接在 NTFS 移动硬盘上运行，权限和符号链接会出问题。
2. 安装依赖。会在包内创建 `.venv`，torch 用 CPU 版即可：
   ```bash
   bash install.sh
   ```
3. 打开 `scripts/real_cell/run_real_cell.py`，在开头填写 `LEFT_IP`、`RIGHT_IP`，或者运行时加 `--left-ip`、`--right-ip`。
4. 以下所有命令都在包的根目录下运行。程序会自动切换到包根目录，日志写在 `outputs/real_runs/<时间>/`。

运行时电脑上不要跑其他重任务。规划延迟会直接影响结果：在 `--time-scale 6` 下，从出帧到动作生效的预算约 0.5–0.8 s（仿真里 8–10 步都验证过）；运行结束时终端打印的 decision p95 应低于 480 ms。

## 3. 部署流程

按顺序执行。前一步不通过，就不要进入下一步。

**步骤 1：本机自检（不连机器人）**
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --dry-run --scenes test_reach_0087
```
用 mock 机器人和 stub 策略走一遍完整流程，并运行软件检查（文件完整性、依赖、BLAS、规划延迟自检）。
- 遇到确认提示时输入 `y`。
- stub 策略把目标曲线当作绳子的估计，所以结束时可能报 E105。这在 dry-run 里是正常的。

**步骤 2：双探针对点（核对两个底座之间的变换）**
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --touch-check
```
保持两台示教器在本地控制模式，由现场操作员使用自由驱动，在工作区的 3 个不同位置让两探针尖端轻触。命令只读取 TCP 坐标。每次差值都要 ≤ 5 mm。超过 5 mm 时先核对底座变换和 TCP 设置。

**步骤 3：运行前安全检查**
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --preflight-only
```
退出自由驱动并切换到远程控制。预检会上传 RTDE 控制脚本，因此先确认两台都没有其他运行中的程序。所有 FAIL 项都必须处理掉。检查内容：
- 文件 sha256、依赖版本、BLAS 是否单线程、CPU 负载
- 规划延迟：p95 超过 80 ms 判 FAIL
- 两台机器人：模式 RUNNING、安全模式 NORMAL、速度滑块 100%、ur_rtde 控制脚本在运行、TCP 偏置
- 两台相机：都在出图、帧率 ≥ 25 Hz、图像不全黑也不过曝
- 日志所在磁盘的剩余空间

**步骤 4：可行性检查（只读，不运动）**
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --check-only
```
逐个场景检查：左臂起点、目标和工作区网格的 IK 与控制器安全限位；右臂整条轨迹的 IK、安全限位和关节速度；两臂之间、球与左臂之间的胶囊间隙。

注意：两臂间隙检查用的是整个工作区网格的保守包络，test_reach_0016 和 test_hold_0085 会判为不通过。按实际策略路径做的仿真回放里，5 个场景的间隙都是正的。确认之后，可以对这两个场景单独加 `--ignore-check`。

**步骤 5：第一次运动，只跑一个场景**
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --scenes test_reach_0087
```
先跑 test_reach_0087：它在所有仿真里都成功，其中包括真实跟踪器和软件在环测试，球绳最小间隙也在 29 mm 以上。每个场景有两次人工确认：
1. `[1/2]`：摆好绳子、清空工作区后输入 `y`，开始归位。左臂直线运动（moveL）到起点，右臂关节运动（moveJ）到规划好的起始关节。
2. 程序检查归位结果：左臂位置误差 ≤ 4 mm，关节分支和仿真一致，右臂关节和规划一致，工具姿态没变。
3. `[2/2]`：确认绳子已静止后输入 `y`，开始运动。

运行中按 Ctrl-C 会让两臂都停止，同时生成报告（E901）。

**步骤 6：其余场景**

建议顺序：test_hold_0085 → test_hold_0116 → test_reach_0090 → test_reach_0016。
- 前三个在真实跟踪器的仿真里都是超时，没有碰撞，所以实机上超时（W001）是预期内的结果。
- test_reach_0016 在真实跟踪器下能成功，但对延迟最敏感，球绳余量也最小，放到最后。
```bash
.venv/bin/python scripts/real_cell/run_real_cell.py --scenes test_hold_0085,test_hold_0116,test_reach_0090
```

## 4. 运行中的自动保护

满足下面任一条件，两臂立即停止（`servoStop`），并生成错误报告。

| 保护 | 阈值（参数） | 错误码 |
|---|---|---|
| 保护性停止、急停、安全模式异常、RTDE 断开、ur_rtde 控制脚本停止 | 每个伺服周期检查（后三项每 10 个周期检查一次） | E101 |
| 左臂实际位置与近 0.2 s 内指令的最小偏差 | 30 mm（`--max-follow-m`） | E102 |
| 右臂实际关节与近 0.2 s 内指令的最小偏差 | 0.05 rad（`--max-follow-rad`） | E103 |
| 两臂之间、球与左臂之间的胶囊间隙（按实际关节，每个周期计算） | 0 mm（`--abort-gap-m`） | E104 |
| 球绳估计间隙 | 2 mm（`--abort-surface-m`） | E105 |
| 跟踪失效持续时间 | 3 s 真实时间（`--max-stale-s`） | E202 |
| 开始后一直没有进入 tracking | 5 s 仿真时间（`--max-start-s`；6 倍下 30 s） | E204 |
| 机器人数据超过 0.1 s 仿真时间没更新（控制环被拖慢） | 0.1 s（6 倍下 0.6 s） | E205 |
| 策略指令非法，或超过 0.4 mm/步（一步 = 8 ms 仿真时间） | — | E303 |
| 30 s 仿真时间内没有成功 | 30 s（6 倍下 180 s） | W001 |

此外，左臂指令点如果越出工作区不超过 1 mm，会被投影回边界上（`--snap-m`）；超过就保持原指令不动。很多场景的起点本身就在工作区边界上，这样处理可以避免 0.1 mm 的定位误差被误判为越界。

## 5. 错误码

出现错误时，终端会打印一个报告块，包含：错误码、含义、测到的数值、两台机器人当时的状态、可能原因和处理办法。同时写出 `outputs/real_runs/<时间>/<场景>_error.json`，里面还有最后 25 步日志和 traceback。

| 代码 | 含义 | 程序终止名 | 首先处理 |
|---|---|---|---|
| W001 | 超时：30 s 内未达到成功标准 | `timeout` | 不是安全故障；查看日志里 rmse / end 的走势 |
| E101 | 机械臂保护性停止 / 急停 | `robot_fault` | 在示教器上查看日志并确认原因 |
| E102 | 左臂跟随误差过大 | `left_lag_abort` | 检查左臂周围有无障碍和绳子缠绕 |
| E103 | 右臂跟随误差过大 | `right_lag_abort` | 检查右臂周围 |
| E104 | 两臂之间 / 球与左臂的胶囊间隙低于阈值 | `abort_arm_clearance` | 查看报告中的 gap_arm / gap_ball 值和时间 |
| E105 | 球与绳的估计间隙低于阈值 | `abort_surface_clearance` | 检查绳子是否被碰到、是否需要复位 |
| E201 | 视觉 / 跟踪故障 | `abort_observation_fault` | 检查两个 RealSense 的 USB 连接 |
| E202 | 跟踪长时间失效（observation_stale 超过限制） | `abort_stale_too_long` | 检查遮挡物和光照 |
| E203 | 相机没有画面 | `camera_timeout` | 关闭其他占用相机的程序 |
| E204 | Controller 一直没有进入 tracking 状态 | `abort_never_tracking` | 检查绳子是否在视野内 |
| E205 | 机器人数据过期（控制环超过 0.1 s 没有拿到新状态） | `abort_robot_stale` | 关闭电脑上的其他任务 |
| E206 | 时钟 / 输入异常 | `abort_invalid_robot_clock`, `abort_invalid_clock`, `abort_invalid_input` | 保存报告并反馈；不要重复运行同一配置 |
| E301 | 约束不可行（execute_action 无法给出满足加速度与工作区限制的动作） | `abort_constraint_infeasible` | 查看报告中的 left_cmd 与工作区边界 |
| E302 | 左臂在工作区之外 | `abort_outside_workspace`, `outside_workspace_at_start` | 重新归位；检查 TCP 偏置是否为探针尖端 [0, 0, 0.165] |
| E303 | 策略输出了非法指令（非有限值或超过速度上限） | `abort_bad_command` | 保存报告并反馈 |
| E401 | Controller 异常 | `controller_error: ...` | 保存报告并反馈 |
| E402 | 伺服环异常 | `servo_error: ...` | 检查网络和机器人状态；确认示教器处于远程控制模式 |
| E403 | 工具姿态在规划后被改变 | `orientation_changed` | 重新运行该场景（会重新规划） |
| E501 | 无法连接机器人（RTDE） | — | ping 机器人 IP；示教器切到远程控制；启用 RTDE 服务 |
| E601 | 场景可行性检查未通过 | — | 按 fail 列表处理；不要用 --ignore-check 强行运行，除非确认是模型过保守 |
| E602 | 归位失败，或归位后检查未通过 | — | 人工把机械臂移到接近仿真初始构型的位置后重跑 |
| E700 | 运行前安全检查未通过 | — | 逐项处理 FAIL 项后重新运行 preflight |
| E901 | 人为中止（Ctrl-C） | `user_interrupt` | 确认机械臂已停止；需要时人工复位绳子 |
| E902 | 运行被意外停止 | `stopped` | 保存报告并反馈 |
